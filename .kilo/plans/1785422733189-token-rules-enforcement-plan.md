# Enforcement of token-saving rules via kilo.json permissions

## Контекст

`.kilo/rules/main.md` существует, но при реализации presigned-upload фичи не
влиял на поведение: агент прочитал ~15 файлов целиком вместо точечного поиска,
несмотря на строку "Не читай файлы целиком — ищи через `rg`". Правило было
прочитано, но не является ограничением — это просто текст в системном промпте.

Единственный механизм, который реально блокирует поведение агента — это
`permission` в `kilo.json` (project-level, `./kilo.json`). Сейчас файла нет
(проверено — `glob kilo.json` ничего не нашёл).

Дополнительно решено: разработка переезжает в WSL2 к прод-паритету (Linux,
Docker, ffmpeg, faster-whisper, CUDA-passthrough). Это снимает открытый вопрос
№1 из предыдущего плана (`1785422733189-presigned-direct-upload-plan.md`) и
означает, что `rg`/`fd` будут доступны в среде разработки (в отличие от текущей
Windows-сессии, где `rg` не найден).

## Что этот план делает и не делает

Делает: описывает конкретный `kilo.json` с permissions, который **технически**
запрещает агенту читать/трогать то, что запрещено в `main.md`, вместо того чтобы
полагаться на то, что агент "не забудет".

Не делает: не переписывает исходный код проекта, не мигрирует окружение в WSL
(это отдельная задача — переезд репозитория, пересборка `.venv` под Linux,
проверка ffmpeg/CUDA внутри WSL).

## Ограничение, которое нужно понимать

`permission.read`/`glob`/`grep` с `deny` блокируют вызов **инструмента** Read/Glob/Grep
на путь. Они не блокируют:
- Bash-команды типа `cat`, `type`, `Get-Content` на те же пути (агенту явно
  запрещено ими пользоваться по общим правилам инструментов, но это не жёсткое
  ограничение permissions)
- то, что модель один раз уже видела в контексте текущей сессии

Поэтому реальная защита — комбинация: permissions (жёсткая для Read/Glob/Grep) +
`.gitignore`/структура проекта (эти каталоги и так не должны существовать в
воркспейсе для чтения) + `/clear` между задачами (дисциплина пользователя, не
автоматизируется).

## Предлагаемый `kilo.json`

Создать `C:\Users\loght\OneDrive\Desktop\TakeFlow\kilo.json`:

```jsonc
{
  "$schema": "https://app.kilo.ai/config.json",
  "permission": {
    "read": {
      "**/.venv/**": "deny",
      "**/__pycache__/**": "deny",
      "**/*.pyc": "deny",
      "**/node_modules/**": "deny",
      "**/uv.lock": "ask",
      "**/*.env": "deny",
      "**/*": "allow"
    },
    "grep": {
      "**/.venv/**": "deny",
      "**/__pycache__/**": "deny",
      "**/node_modules/**": "deny",
      "**/*": "allow"
    },
    "glob": {
      "**/.venv/**": "deny",
      "**/__pycache__/**": "deny",
      "**/node_modules/**": "deny",
      "**/*": "allow"
    },
    "edit": {
      "**/uv.lock": "deny",
      "**/*": "ask"
    },
    "bash": "ask"
  }
}
```

Обоснование по каждому пункту:

| Правило | Почему |
|---|---|
| `read`/`grep`/`glob` deny на `.venv`, `__pycache__`, `node_modules` | Прямое исполнение "Не читай `.venv/` или `__pycache__/`" из `main.md`. Замечено, что под `.kilo/node_modules/` лежит посторонний JS-пакет (multipasta/zod/uuid) — вероятно установка какого-то CLI-тула; блокировка чтения защищает и от него |
| `read` deny на `.env`, `ask` на `uv.lock` | `.env` — секреты, `uv.lock` — "не трогать вручную" из rules; `ask` вместо `deny`, потому что иногда легитимно нужно посмотреть версию пакета |
| `edit` deny на `uv.lock` | Жёсткое исполнение "Не трогать `uv.lock` вручную — только через `uv add/remove`" — сейчас это правило нарушалось (файл редактировался как побочный эффект `uv add`, что нормально, но прямое ручное редактирование должно быть заблокировано) |
| `edit` ask по умолчанию | Соответствует текущему поведению (нужно подтверждение перед правками) — не ужесточаем без запроса |
| `bash: ask` | Ловит попытки `cat`/`grep -r` в обход дедики-тулов; сейчас агент один раз попытался вызвать `rg` через bash при недоступности инструмента — с `ask` пользователь увидит и сможет остановить |

## Изменение в `.kilo/rules/main.md`

Текущая строка `поиск контента: rg` неверна для Windows-сессии (rg не найден,
проверено этой сессией). После переезда в WSL это будет корректно. Правки:

1. Оставить строку как есть — WSL решает несоответствие.
2. Добавить одну строку прямо про enforcement, чтобы агент не думал, что
   `main.md` — это единственный механизм:

```markdown
## Токены
- .venv/__pycache__/node_modules физически недоступны через permissions в kilo.json — не пытайся их читать
- /clear между несвязанными задачами — это на пользователе, не забывай напоминать
```

## Задачи

1. Создать `kilo.json` в корне репозитория с блоком выше.
2. Дописать секцию "Токены" в `.kilo/rules/main.md` (2 строки, не превышает лимит 80 строк — сейчас 29, будет 33).
3. Проверить permissions: попросить агента прочитать файл из `backend/.venv/` в новой сессии — ожидается отказ инструмента без подтверждения (для `deny`) или запрос подтверждения.
4. Не переносить сейчас переезд в WSL — отдельная задача (вне рамок этого плана), но зафиксировать её как следующий шаг.

## Валидация

- Новая сессия: `Read backend/.venv/pyvenv.cfg` → должно быть отклонено инструментом, а не просто "решением агента не читать".
- Новая сессия: `Grep pattern:"." path:"backend/__pycache__"` → должно быть отклонено.
- `git diff kilo.json .kilo/rules/main.md` — просмотреть перед принятием.

## Открытый вопрос

Ставить `read` на `.env` как `deny` полностью (текущее предложение) или `ask`
(на случай, если разработчику самому нужно попросить агента сверить переменную)?
Рекомендация: `deny`, потому что чтение секретов агентом даже с последующим
неотображением значений — риск, которого легко избежать, а переменные .env.example
и так открыты для чтения.
